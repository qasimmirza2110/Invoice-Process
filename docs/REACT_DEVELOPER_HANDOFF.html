What calls what — the 10-minute overview

The backend is a Java Spring Boot program that stores invoices in a PostgreSQL database. It has no web pages of its own: it only answers API requests — small HTTP messages such as “give me the list of users” — with JSON data. Your React app is the only user interface.

Opening the API's own address (/) in a browser answers 401. That is expected — there is no page there. The health check is GET /api/health → 200 {"status":"UP"}. On Render's Free plan the first request after 15 idle minutes can take about a minute while the service wakes up.

One request, from click to screen

  1. The user opens the Admin “Users” page. React calls api('/api/admin/users').
  2. The API client adds Authorization: Bearer <accessToken> (the token it got at login and keeps in memory) and sends GET /api/admin/users to the Vite dev server.
  3. The Vite proxy forwards the request unchanged to the API.
  4. Spring Security checks the token (who are you?) and the role (are you ADMIN?). Missing/invalid/expired token → 401; wrong role → 403.
  5. The controller calls a service, which reads PostgreSQL and turns database rows into a DTO (a fixed JSON shape such as UserResponse).
  6. The JSON travels back to the browser; React stores it in state and renders the table.

What lives where

Backend decides (never only in React)

  • Who is logged in, and what each role may call
  • Which objects a user may see (vendor = own, reviewer = assigned, admin = all; others get 404)
  • PDF checks, duplicates, the invoice status rules, version conflicts (409)
  • Validation of every field (400 with fieldErrors, 422 for business rules)

React decides

  • Screens, navigation and what to show for each role
  • Forms and friendly early checks (the server still decides)
  • Loading, empty, error, retry and session-expired states
  • Layout, accessibility, responsiveness

Hiding a menu item is not security; it is only convenience. The API refuses anything a role may not do, whatever React shows.

Roles and the invoice lifecycle

Every account has exactly one role, returned at login (user.role) and by GET /api/auth/me. There is no sign-up page: the first ADMIN is created by the backend owner, and only an ADMIN creates further users.

RoleDoesSeesMain screens
VENDORUploads invoice PDFs in batchesOnly own batches and invoicesThis week (dashboard), New batch + upload, My batches, Batch detail, Invoice detail (read-only)
REVIEWERCorrects extracted data and submits one exact version for approvalOnly invoices assigned to themToday (dashboard), Assigned to me, Invoice review (PDF left, editable data right)
ADMINManages users, categories, assignment, decisions, queueEverythingDashboard, Intake & assignment, Waiting for approval, Failed extractions, Approved and rejected, Users, Categories, Queue status

Invoice lifecycle (statuses come from the backend)

  1. Vendor creates a batch (category, source), uploads PDFs one by one → each accepted file becomes an invoice with status QUEUED. “Accepted” means stored and waiting — not extracted.
  2. The extraction worker sends the PDF to Gemini (only where the owner enabled it): QUEUED → PROCESSING → NEEDS_REVIEW (version V1 = what the AI read), or FAILED after 3 attempts.
  3. Admin sets the category and assigns a reviewer who handles that category (this can happen already while the invoice is QUEUED).
  4. Reviewer compares the original PDF with the data, saves corrections — each save is a new, unchangeable version (V2, V3 …) linked to the same original PDF — and submits one exact version: PENDING_APPROVAL.
  5. Admin approves (APPROVED), rejects (REJECTED) or sends it back (NEEDS_REVIEW) after looking at all versions. Decided invoices can be reopened; failed ones requeued.
  6. Vendor sees the current status of each upload in the batch detail.

The one API client

Every component goes through this one file. It keeps the access token in memory, adds the Authorization header, sends JSON or files, parses errors in one way and reports an ended session. Components never call fetch themselves.

// src/api/client.ts
export interface FieldError { field: string; message: string }

/** Shape of every 4xx/5xx body (ErrorResponse) - plus, for uploads, the FileIntakeResponse of a 422. */
export interface ApiErrorBody {
  status: number;
  error?: string;
  message: string;
  path?: string;
  timestamp?: string;
  fieldErrors?: FieldError[] | null;
  errorId?: string;          // only on unexpected 500s: show it as a reference
  code?: string | null;      // only on upload rejections (422), e.g. INVALID_FILE, DUPLICATE_FILE
}

export class ApiError extends Error {
  readonly status: number;
  readonly body: ApiErrorBody;
  constructor(body: ApiErrorBody) {
    super(body.message);
    this.name = 'ApiError';
    this.status = body.status;
    this.body = body;
  }
}

const BASE = import.meta.env.VITE_API_BASE_URL ?? '';   // EMPTY = same origin through the proxy

// The access token lives ONLY in this module's memory: not in localStorage, sessionStorage or a cookie.
// A page reload therefore logs the user out - that is intended.
let accessToken: string | null = null;
export function setAccessToken(token: string | null): void { accessToken = token; }
export function hasAccessToken(): boolean { return accessToken !== null; }

let onSessionEnded: () => void = () => {};
/** SessionProvider registers this: forget the user and show the login page. */
export function setSessionEndedHandler(handler: () => void): void {
  onSessionEnded = handler;
}

type Query = Record<string, string | number | boolean | undefined>;

export interface RequestOptions {
  method?: 'GET' | 'POST' | 'PUT';
  json?: unknown;            // sent as application/json
  form?: FormData;           // sent as multipart/form-data (file upload)
  query?: Query;
  signal?: AbortSignal;
}

export async function api<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const method = options.method ?? 'GET';
  const headers: Record<string, string> = { Accept: 'application/json' };
  if (accessToken) headers.Authorization = `Bearer ${accessToken}`;

  let body: BodyInit | undefined;
  if (options.json !== undefined) {
    headers['Content-Type'] = 'application/json';
    body = JSON.stringify(options.json);
  } else if (options.form) {
    body = options.form;     // do NOT set Content-Type: the browser adds the multipart boundary
  }

  const params = new URLSearchParams();
  for (const [key, value] of Object.entries(options.query ?? {})) {
    if (value !== undefined) params.set(key, String(value));
  }
  const url = BASE + path + (params.toString() ? `?${params.toString()}` : '');

  const response = await fetch(url, { method, headers, body, signal: options.signal });
  const isJson = (response.headers.get('Content-Type') ?? '').includes('application/json');

  if (!response.ok) {
    const parsed: Partial<ApiErrorBody> = isJson ? await response.json() : {};
    const errorBody: ApiErrorBody = {
      ...parsed,
      status: response.status,                         // always the real HTTP status
      message: parsed.message ?? 'Unexpected response from the server.',
    };
    if (response.status === 401 && accessToken) {     // the token expired or was revoked
      accessToken = null;
      onSessionEnded();
    }
    throw new ApiError(errorBody);
  }
  if (response.status === 204) return undefined as T;  // logout-all
  if (isJson) return (await response.json()) as T;
  return (await response.blob()) as unknown as T;      // PDFs
}

Using it

// src/api/auth.ts
import { api, setAccessToken } from './client';
export interface Me { id: number; email: string; name: string; displayName: string; role: 'ADMIN' | 'VENDOR' | 'REVIEWER' }
export interface LoginResponse { accessToken: string; tokenType: 'Bearer'; expiresIn: number; expiresAt: string; user: Me }

export async function login(email: string, password: string): Promise<Me> {
  const result = await api<LoginResponse>('/api/auth/login', { method: 'POST', json: { email, password } });
  setAccessToken(result.accessToken);   // memory only
  return result.user;
}
export function logout(): void { setAccessToken(null); }   // no server call needed
export async function logoutEverywhere(): Promise<void> {
  await api<void>('/api/auth/logout-all', { method: 'POST' });   // revokes ALL tokens of this user
  setAccessToken(null);
}
export const getMe = () => api<Me>('/api/auth/me');

// Upload one file (field name "file"); 202 accepted and 422 rejected both carry a FileIntakeResponse
export function uploadFile(batchId: number, file: File) {
  const form = new FormData();
  form.append('file', file);
  return api<{ fileName: string; accepted: boolean; invoiceId: number | null; status: string | null;
               code: string | null; message: string }>(`/api/batches/${batchId}/files`, { method: 'POST', form });
}
// On 422: catch the ApiError and read error.body.code / error.body.message for that file's row.

Login and the Bearer token — the exact rules

ItemExact behaviour (from source and tests)
LoginPOST /api/auth/login {"email","password"} → 200 {"accessToken","tokenType":"Bearer","expiresIn":1800,"expiresAt":"2026-10-28T10:30:00Z","user":{...}}. No cookie is set.
Every other callHeader Authorization: Bearer <accessToken>. Only GET /api/health and login work without it.
Where the token is readOnly that header — never a cookie, a URL parameter or a request body.
Storage in ReactMemory only (module variable / context). Not localStorage, not sessionStorage. Never log it, never put it in a URL.
Lifetime / refresh30 minutes (expiresIn), no refresh token. After that the next call returns 401 → show login, then return the user to where they were.
RoleRead from the database on every request (not from the token). A role change or disabling takes effect on the next request.
LogoutForget the token in memory. “Log out everywhere” = POST /api/auth/logout-all (revokes every token of this user on the server). There is no /api/auth/logout route.
CSRFNot needed and not used: browsers never attach an Authorization header by themselves, so another website cannot send authenticated requests in the user's name.
401 / 403401 "Please log in." (with WWW-Authenticate: Bearer) for a missing, malformed, expired, revoked or wrongly signed token or a disabled account; 403 for a valid token with the wrong role.
Login lock5 failed logins per e-mail or per client address → locked for 15 minutes (429).

Sequence

  1. App start: no token in memory → show the login page (no error banner).
  2. Login form: POST /api/auth/login. 200 → store accessToken in memory, route by user.role. 401 → one generic “wrong e-mail or password”. 429 → show the lock message.
  3. While logged in: any 401 → the client forgets the token, the session provider shows login (“your session ended”).
  4. Logout: forget the token and clear all cached data (e.g. queryClient.clear()).

Errors and UI states

Every 4xx/5xx has the same JSON shape (upload rejections additionally carry code):

{ "timestamp": "2026-10-27T10:15:00", "status": 409, "error": "Version conflict",
  "message": "Version 2 is not the submitted, current version (submitted: 2, current: 3). Reload before deciding.",
  "path": "/api/invoices/41/approve", "fieldErrors": null }
StatusMeans hereUI reaction
400Invalid request / field validation (fieldErrors); upload request over 11 MBShow each message next to its field; do not resend unchanged
401No, expired, revoked or invalid token, or disabled account — on the login form: wrong e-mail or passwordForget the token, go to login (keep the user's place); on the login form show the message
403Valid token, wrong role“Not allowed” — do not retry
404Not found or not yours (same answer on purpose)“Not found” — never hint that it exists
409State or version conflict, duplicate e-mail, closed/full batch, last admin, switched-off endpointReload the object, show the message; never auto-resend
415Wrong Content-TypeDeveloper error — fix the request
422Content rejected by a rule (upload code, submit check)Show code / message / fieldErrors
429Login locked for 15 minutesShow the message; do not retry automatically
500Server or storage error: database unavailable, a stored PDF failing its integrity check, or the PDF bucket unreachable during an upload (the file was not accepted)“Something went wrong (reference errorId)” — never a stack trace

Not every route returns every status; the per-route lists are in REACT_BACKEND_HANDOFF.md. 502 exists only on the legacy extraction route.

States every screen needs

  • Loading: skeleton or spinner with an accessible label; up to a minute after idle (cold start) — say so.
  • Empty: an explanation and the next action (“No batches yet — create one”).
  • Error: the server message in a visible role="alert" region.
  • Retry: manual, only for network errors, 429 and 5xx.
  • Session expired: keep the place, show login, return after login.

First integration session

Read-only first

  • Open the dev app; the network tab shows GET /api/health → 200 {"status":"UP"}.
  • GET /api/auth/me without a token → 401 with WWW-Authenticate: Bearer; no cookie appears.

Then, with the test account the backend owner gave you

  • Log in → 200 with accessToken and user; no Set-Cookie header.
  • GET /api/auth/me with the Bearer header → 200 with your role.
  • A wrong password shows the generic 401 message.
  • Navigation matches the role; a forbidden URL typed by hand shows “not allowed” / “not found”.
  • Only with the owner's go-ahead: create, change or upload data — synthetic values and sample PDFs only.
  • Log out → the token is gone from memory; the next protected call is not sent or gets 401.

Reporting an API mismatch

Send the backend owner: the route and method, the request body (without any password), the HTTP status, the response body, the errorId if present, and what this guide or openapi.yaml says should happen. Never send tokens or passwords — remove the Authorization header from any copied request.

Hosting the React app later

  • Simplest: one origin. One public hostname serves the React build and forwards /api/* to the backend (reverse proxy / path-based routing). No CORS needed.
  • Separate origin (e.g. React on its own host): possible with Bearer tokens. The backend owner adds your exact origin to INVOICE_CORS_ALLOWED_ORIGINS; then set VITE_API_BASE_URL to the API's public URL (a public value, not a secret). Never ask for *.
  • In both cases the token stays in memory and is sent only in the Authorization header.

Definition of done

  • All data comes from the documented routes through the one API client; no invented endpoints or fields.
  • Login, logout, session expiry (401) and the Bearer header work in the browser (shown live).
  • Navigation and screens per role; forbidden and not-found states handled.
  • Admin: users, categories, reviewer categories, intake/assignment, batches, queue status, dashboard, approvals, failed, decided.
  • Vendor: dashboard, batch create, one-by-one upload with per-file results, close, batch detail.
  • Reviewer: dashboard, assigned list, PDF on the left (blob URL), editable data on the right, save as new version, versions list, submit.
  • Loading, empty, error, retry and validation states everywhere; responsive to phone width; keyboard-only usable.
  • No secrets in code or VITE_*; no token in localStorage/sessionStorage; no real data in the repo.
  • npm run lint, npm test and npm run build pass.

Glossary

API / endpoint / route
A URL plus an HTTP method that the backend answers, e.g. GET /api/admin/users.
Request / response
The message the browser sends (method, path, headers, optional body) and the backend's answer (status code, headers, body).
HTTP status
A number in the response: 2xx success, 4xx the request was not accepted, 5xx the server failed.
JSON / DTO
JSON is the text data format; a DTO (data transfer object) is the fixed shape of one JSON response or request, e.g. UserResponse.
Role
VENDOR, REVIEWER or ADMIN — decides which routes an account may call.
JWT / access token
A signed text the backend issues at login. Whoever holds it is treated as that user for 30 minutes, so keep it in memory and never share it.
Bearer header
Authorization: Bearer <token> — how every request proves who sends it.
CSRF
Cross-site request forgery: another website making your browser send a request with credentials the browser adds by itself (cookies). Not possible here because the token is only ever added by your own code.
Origin / same-origin
Scheme + host + port of a page. Same-origin means the page and the API share all three.
CORS
Browser rules for calls to another origin. Off by default here; the owner can allow exact origins.
Proxy
The Vite dev server forwarding /api/* to the real API, so the browser only talks to one origin.
Multipart / FormData
The request format for file uploads; the browser builds it from a FormData object.
Version
One saved state of an invoice's data. V1 is what the AI extracted; each reviewer save adds V2, V3…; none is ever changed afterwards.
