1. Project overview

The Invoice Process backend receives invoice PDFs from vendors, extracts their data, lets reviewers correct it and lets admins approve or reject it — with a complete, immutable version history and audit trail.

React app (you build it)→Spring Boot REST API→ PostgreSQL+PDF storage+Gemini extraction (off in demo)
  • The repository's main branch is API-only. It serves no HTML, CSS or JavaScript; GET / answers 401. The old vanilla-JS pages were removed — do not look for them or copy from them. The React app is a new, separate project.
  • Roles: VENDOR uploads, REVIEWER corrects and submits invoices assigned to them, ADMIN manages users, categories, assignment, decisions and the queue. One role per user.
  • Format: JSON, except uploads (multipart/form-data) and the original PDF (application/pdf). Dates: "2026-10-06"; timestamps: "2026-10-16T11:00:00" (no zone).

Invoice lifecycle (source: WorkflowTransitions)

PROCESSINGNEEDS_REVIEW / QUEUED / FAILEDExtraction stored / retry / attempts used upNo
NEEDS_REVIEWPENDING_APPROVALAssigned reviewer submits an exact versionNo data in this state
PENDING_APPROVALAPPROVED / REJECTED / NEEDS_REVIEWAdmin approves / rejects / sends backNo data in this state
APPROVED / REJECTEDNEEDS_REVIEWAdmin reopens (reason required)No data in this state
FAILEDQUEUEDAdmin requeues (reason required)No data in this state

Consequence for the demo: you can build and click through login, user and category administration, batch upload, invoice lists, the intake board, assignment, dashboards and session handling. Review, submit and approval are unavailable in the demo because extraction is disabled: nothing moves an invoice out of QUEUED, so no invoice ever reaches NEEDS_REVIEW. Build those screens against the contract only (no fake data, no simulated success) and label them "not available in the demo". Agree with the backend owner how they are demonstrated.

The backend owns

  • Authentication, token revocation, role checks per URL
  • Per-object visibility (vendor = own, reviewer = assigned; others get 404)
  • CSRF, file type/size/signature checks, duplicate detection
  • The status machine and the exact-version rules (409)
  • Invoice arithmetic and format checks, version history, audit events
  • Password rules, "last enabled admin" protection, login lockout

The frontend owns

  • Screens, navigation and role-aware visibility (from Me.role)
  • Forms, client-side convenience checks (the server still decides)
  • Loading, empty, error, retry and session-expiry states
  • Upload progress per file, polling while invoices are queued
  • PDF preview with a fallback when the file is gone
  • Accessibility, responsiveness and consistent design

5. Authentication and CSRF

ItemExact behaviour
Session cookieINVOICE_PROCESS_AUTH — HttpOnly; Secure; SameSite=Strict; Path=/, no Domain, lifetime 30 minutes. A signed JWT your code never sees.
RefreshNone. After 30 minutes the next call returns 401 → show login.
RoleNot in the token; read from the database on every request. Use GET /api/auth/me.
CSRF cookieXSRF-TOKEN (readable by JavaScript, Path=/), handed out on the first response — also anonymous ones such as GET /api/health or a 401 from /api/auth/me.
CSRF headerEvery POST/PUT/DELETE, including login: X-XSRF-TOKEN: <current XSRF-TOKEN value>. Missing → 403 before authentication.
Token rotationA new XSRF-TOKEN at login and at logout; otherwise stable. Read the cookie when sending, never cache it.
Credentials modecredentials: 'same-origin' (the fetch default). No 'include' needed — and it would not help cross-origin.
CORSNone, on purpose (tested: no Access-Control-Allow-Origin, also for http://localhost:5173).

Sequence

  1. GET /api/auth/me → 200: route by role; 401: show login (this response sets XSRF-TOKEN).
  2. POST /api/auth/login with X-XSRF-TOKEN and {email, password} → 200 Me. 401: one generic "wrong e-mail or password". 429: locked (5 failures → 15 minutes).
  3. Every later unsafe call: read XSRF-TOKEN again and send it as the header.
  4. Logout: POST /api/auth/logout (CSRF) → 204; clear all cached data.
function xsrfToken() {
  const m = document.cookie.match(/(?:^|; )XSRF-TOKEN=([^;]*)/);
  return m ? decodeURIComponent(m[1]) : '';
}
await fetch('/api/auth/login', {
  method: 'POST',
  credentials: 'same-origin',
  headers: { 'Content-Type': 'application/json', Accept: 'application/json', 'X-XSRF-TOKEN': xsrfToken() },
  body: JSON.stringify({ email, password }),   // typed by the user - never hard-coded
});

Postman succeeding does not prove the browser works. Postman ignores SameSite and has no origin. Verify login, /api/auth/me and one POST in the browser through the dev proxy, with the network tab open. The proxy route is designed for and its backend side is tested, but it has not yet been exercised in a browser against the deployed demo — you will be the first to confirm it.

The cookies are Secure. Chromium-based browsers accept that on http://localhost; if another browser shows a 200 login followed by 401, run the dev server over HTTPS.

Production frontend hosting is a separate, open decision: it must also be same-origin (one hostname serving React and forwarding /api/*). A Render Static Site rewrite to the API is a candidate, but forwarding of POST bodies and cookies has not been verified.

6. API errors, loading and empty states

Every 4xx/5xx — from controllers and from the security filters — has one shape:

{ "timestamp": "2026-10-23T10:15:00", "status": 409, "error": "Version conflict",
  "message": "Version 2 is not the submitted, current version (submitted: 2, current: 3). Reload before deciding.",
  "path": "/api/invoices/41/approve", "fieldErrors": null }

message is always safe to show. fieldErrors (some 400/422) belong next to their field. errorId appears only on unexpected 500s — show it as a reference.

StatusUsed forUI reaction
400Malformed request, field validation, file too largeShow message / field errors; do not resend unchanged
401No or expired session; login: wrong e-mail or passwordGo to login with "your session ended" (on the login form: the message)
403Wrong role, or missing CSRF headerCSRF message: one GET /api/auth/me, then let the user retry once. Otherwise "not allowed"
404Not found or not yours"Not found" — never hint that it exists
409State or version conflict, duplicate e-mail, closed batch, switched-off legacy endpointReload the object, show the message; never auto-resend
415Wrong Content-TypeDeveloper error — fix the request
422Rule rejected the content (upload rejected, submit check failed)Show code/message/fieldErrors
429Login lockedShow the message; retry later
500Unexpected error (also a stored PDF failing its SHA-256 check)"Something went wrong (reference errorId)"

Not every route returns every status — section 4 lists the main ones per route; the handoff document lists them exhaustively. 502 exists only for the legacy extraction route, which is off.

States every screen needs

  • Loading: skeletons or spinners with an accessible label; allow up to about a minute on the first request after idle (cold start) and say so.
  • Empty: a friendly explanation and the next action (for example "No batches yet — create one").
  • Error: the server message in a visible, role="alert" region; never a raw stack or JSON dump.
  • Retry: manual, for network errors, 429 and 5xx only; never automatic for 4xx.
  • Session expiry: keep the user's place, show login, return afterwards.

7. Free-demo limitations

Synthetic data only. No real customer accounts, names, e-mail addresses, invoices, documents or credentials — ever. Accounts must end in @example.test. Every response carries X-Invoice-Demo: ephemeral-synthetic-only; show a "Demo environment" badge.

8. React implementation requirements

Suggested stack: React + TypeScript + Vite — a practical default (fast, built-in proxy, types checkable against openapi.yaml), not a backend requirement.

Structure

  • src/api/client.ts — the only place that calls fetch: CSRF header, JSON vs multipart, error parsing, 401 handling
  • src/api/*.ts — one module per domain (auth, batches, invoices, admin, dashboards)
  • Types generated from or checked against openapi.yaml
  • Route guards from Me.role; the server still decides

Quality bar

  • Clean, consistent, responsive down to phone width
  • Keyboard-friendly, visible focus, labelled controls, role="alert" errors
  • Loading, empty, error, retry, validation and session-expiry states everywhere
  • Uploads one file at a time with per-file status (202 / 422)
  • PDF preview with "open in new tab" and a "file no longer available" state

Never

  • Invent endpoints, fields or statuses, or fake success responses.
  • Store passwords or tokens in localStorage/sessionStorage — the session is the HttpOnly cookie.
  • Put secrets in VITE_* variables or commit .env.local.
  • Do money maths with JavaScript floats — send amounts as strings.
  • Ask for CSRF, cookies or CORS to be relaxed to fix a frontend error.
  • Mock a missing backend feature silently — report it to the backend owner.

Setup steps and a complete client: react-handoff/README.md.

Known gaps — do not work around them

  • No password-reset, self-registration or "change my password" endpoint; accounts are created by an admin.
  • No refresh token; no total count in list responses; no push updates (poll: batch detail about every 10 s, stop when the tab is hidden).
  • No endpoint to delete users, batches or invoices.
  • Review and approval data cannot be produced in the free demo (no extraction).

Confirm with the backend owner before coding

  • How the reviewer and approval screens will be demonstrated without extraction.
  • Which synthetic accounts exist for each role — planned: one ADMIN, two VENDOR, two REVIEWER, all @example.test (credentials are shared separately, never in this package).
  • Whether cloud-picker upload is in scope (it is browser-side work and not live-tested).
  • The intended production frontend hosting (must be same-origin).

10. Senior-demo acceptance criteria

Run through these live, with the browser's network tab visible. All checks are manual unless your project adds automated tests; nothing on this page has been verified against the deployed API except the health check in the status table.

  • Start logged out: GET /api/auth/me 401, login screen shown, XSRF-TOKEN cookie present.
  • Log in with a synthetic account → X-XSRF-TOKEN sent, 200 Me, role-specific navigation.
  • Wrong password → generic 401 message; no hint whether the e-mail exists.
  • Remove the CSRF header (devtools or a test hook) → 403 handled with the retry flow.
  • Each role sees only its screens; a forbidden URL typed by hand shows "not allowed" / "not found", never a crash.
  • Vendor: create batch, upload one fixture PDF (202, QUEUED), upload a non-fixture file (422 NOT_A_DEMO_FIXTURE) and the same fixture again (422 DUPLICATE_FILE), close the batch.
  • Admin: create a synthetic user (@example.test), category, assignment; a non-test domain shows the 400 message.
  • PDF preview works — and a missing demo PDF shows a friendly message (explain that demo files are ephemeral).
  • Session expiry (wait 30 minutes or log out in another tab) → next action leads to login and back.
  • Cold start after idle shows a patient loading state.
  • Phone-width layout: navigation, tables and forms usable; keyboard-only run-through of login and upload.
  • State clearly which screens are contract-only in the demo (review and approval).
