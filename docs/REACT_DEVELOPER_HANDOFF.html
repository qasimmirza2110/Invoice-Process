What calls what — the 10-minute overview

The backend is a Java Spring Boot program that stores invoices in a PostgreSQL database. It has no web pages of its own: it only answers API requests — small HTTP messages such as “give me the list of users” — with JSON data. Your React app is the only user interface. It runs in the browser, asks the API for data and shows it.

One request, from click to screen

  1. The user opens the Admin “Users” page. React calls api('/api/admin/users').
  2. The browser sends GET /api/admin/users to the Vite dev server (same origin as the page) and automatically attaches the login cookie.
  3. The Vite proxy forwards the request unchanged to the deployed API.
  4. Spring Security checks the cookie (who are you?) and the role (are you ADMIN?). No/invalid cookie → 401; wrong role → 403. Unsafe methods must also carry the CSRF header → otherwise 403.
  5. The controller calls a service, which reads PostgreSQL and turns database rows into a DTO (a fixed JSON shape such as UserResponse).
  6. The JSON travels back through the proxy to the browser; React stores it in state and renders the table.

React never talks to PostgreSQL and never reads data from an HTML page. Every piece of data — including all Admin data — comes from one of the 47 API routes below, through your single API client.

What lives where

Backend decides (never only in React)

  • Who is logged in, and what each role may call
  • Which objects a user may see (vendor = own, reviewer = assigned, admin = all; others get 404)
  • CSRF, file checks, duplicates, the invoice status rules, version conflicts (409)
  • Validation of every field (400 with fieldErrors, 422 for business rules)

React decides

  • Screens, navigation and what to show for each role
  • Forms and friendly early checks (the server still decides)
  • Loading, empty, error, retry and session-expired states
  • Layout, accessibility, responsiveness

Hiding a menu item is not security; it is only convenience. The API refuses anything a role may not do, whatever React shows.

The one API client

Every component goes through this one file. It adds the CSRF header, sends JSON or files, parses errors in one way and reports an expired session. Components never call fetch themselves.

// src/api/client.ts
export interface FieldError { field: string; message: string }

/** Shape of every 4xx/5xx body (ErrorResponse) - plus, for uploads, the FileIntakeResponse of a 422. */
export interface ApiErrorBody {
  status: number;
  error?: string;
  message: string;
  path?: string;
  timestamp?: string;
  fieldErrors?: FieldError[] | null;
  errorId?: string;          // only on unexpected 500s: show it as a reference
  code?: string | null;      // only on upload rejections (422), e.g. NOT_A_DEMO_FIXTURE
}

export class ApiError extends Error {
  readonly status: number;
  readonly body: ApiErrorBody;
  constructor(body: ApiErrorBody) {
    super(body.message);
    this.name = 'ApiError';
    this.status = body.status;
    this.body = body;
  }
}

const BASE = import.meta.env.VITE_API_BASE_URL ?? '';   // keep EMPTY: same origin through the proxy

/** Read at the moment of sending: login and logout replace the token. */
export function readXsrfToken(): string {
  const match = document.cookie.match(/(?:^|;\s*)XSRF-TOKEN=([^;]*)/);
  return match ? decodeURIComponent(match[1]) : '';
}

let onUnauthorized: () => void = () => {};
/** SessionProvider registers this; it only acts when the user WAS logged in. */
export function setUnauthorizedHandler(handler: () => void): void {
  onUnauthorized = handler;
}

type Query = Record<string, string | number | boolean | undefined>;

export interface RequestOptions {
  method?: 'GET' | 'POST' | 'PUT';
  json?: unknown;            // sent as application/json
  form?: FormData;           // sent as multipart/form-data (file upload)
  query?: Query;
  signal?: AbortSignal;
}

export async function api<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const method = options.method ?? 'GET';
  const headers: Record<string, string> = { Accept: 'application/json' };
  if (method !== 'GET') headers['X-XSRF-TOKEN'] = readXsrfToken();

  let body: BodyInit | undefined;
  if (options.json !== undefined) {
    headers['Content-Type'] = 'application/json';
    body = JSON.stringify(options.json);
  } else if (options.form) {
    body = options.form;     // do NOT set Content-Type: the browser adds the multipart boundary
  }

  const params = new URLSearchParams();
  for (const [key, value] of Object.entries(options.query ?? {})) {
    if (value !== undefined) params.set(key, String(value));
  }
  const url = BASE + path + (params.toString() ? `?${params.toString()}` : '');

  const response = await fetch(url, { method, headers, body, credentials: 'same-origin', signal: options.signal });
  const isJson = (response.headers.get('Content-Type') ?? '').includes('application/json');

  if (!response.ok) {
    const parsed: Partial<ApiErrorBody> = isJson ? await response.json() : {};
    const errorBody: ApiErrorBody = {
      ...parsed,
      status: response.status,                         // always the real HTTP status
      message: parsed.message ?? 'Unexpected response from the server.',
    };
    if (response.status === 401) onUnauthorized();
    throw new ApiError(errorBody);
  }
  if (response.status === 204) return undefined as T;  // logout, logout-all
  if (isJson) return (await response.json()) as T;
  return (await response.blob()) as unknown as T;      // PDFs
}

Using it

// src/api/auth.ts
import { api, readXsrfToken } from './client';
export interface Me { id: number; email: string; name: string; displayName: string; role: 'ADMIN' | 'VENDOR' | 'REVIEWER' }

/** App start: 200 = logged in; ApiError 401 = logged out (this call also hands out XSRF-TOKEN). */
export const getMe = () => api<Me>('/api/auth/me');

export async function login(email: string, password: string): Promise<Me> {
  if (!readXsrfToken()) {
    await api('/api/health');            // any anonymous GET sets the XSRF-TOKEN cookie
  }
  return api<Me>('/api/auth/login', { method: 'POST', json: { email, password } });
}
export const logout = () => api<void>('/api/auth/logout', { method: 'POST' });

// Upload one file (field name "file"); 202 accepted and 422 rejected both carry a FileIntakeResponse
export function uploadFile(batchId: number, file: File) {
  const form = new FormData();
  form.append('file', file);
  return api<{ fileName: string; accepted: boolean; invoiceId: number | null; status: string | null;
               code: string | null; message: string }>(`/api/batches/${batchId}/files`, { method: 'POST', form });
}
// On 422: catch the ApiError and read error.body.code / error.body.message for that file's row.

PDF preview: a link or <iframe> with src="/api/invoices/{id}/document" works through the proxy (same origin, cookie sent automatically). Handle 404 as “original file no longer available in the demo”.

Login, cookies and CSRF — the exact rules

ItemExact behaviour (from source)
Session cookieINVOICE_PROCESS_AUTH: HttpOnly; Secure; SameSite=Strict; Path=/, no Domain, 30 minutes. A signed JWT the browser manages; JavaScript can never read it and must not try. Never store it in localStorage or React state.
RefreshNone. After 30 minutes the next request returns 401 → show login, then return the user to where they were.
RoleRead from the database on every request (not in the token). A role change or disabling takes effect immediately.
CSRF cookieXSRF-TOKEN (readable by JavaScript, Path=/), set on the first response — also anonymous ones like GET /api/health or a 401 from GET /api/auth/me.
CSRF headerEvery POST and PUT (the only unsafe methods this API has), login included: X-XSRF-TOKEN: <current cookie value>. Missing or wrong → 403, checked before authentication.
RotationA new token at login and at logout. Read the cookie immediately before each request; never keep it in state.
Credentialscredentials: 'same-origin' through the Vite proxy. The browser code never calls the onrender.com URL directly.
CORSNone, on purpose. A page on another origin gets no permission, cannot read XSRF-TOKEN, and the SameSite=Strict cookie is not sent cross-site.
Login lock5 failed logins per e-mail or per client address → locked for 15 minutes (429).

Sequence

  1. App start: GET /api/auth/me. 200 → logged in, route by role. 401 → show login (no error banner).
  2. Login form: POST /api/auth/login {email, password} with X-XSRF-TOKEN. 200 → Me. 401 → one generic “wrong e-mail or password”. 429 → show the lock message.
  3. While logged in: any 401 → session ended. Any 403 whose message mentions CSRF → do one GET /api/auth/me and let the user retry once.
  4. Logout: POST /api/auth/logout → 204; clear all cached data. “Log out everywhere”: POST /api/auth/logout-all.

Postman succeeding does not prove the browser works (Postman ignores SameSite and origins). The proxy route is designed and its backend side is tested, but it has not yet been exercised in a browser against the deployed demo — you will be the first to confirm it. Chromium-based browsers accept the Secure cookies on http://localhost; if another browser shows a 200 login followed by 401, run the dev server over HTTPS.

Errors and UI states

Every 4xx/5xx has the same JSON shape (upload rejections additionally carry code):

{ "timestamp": "2026-10-27T10:15:00", "status": 409, "error": "Version conflict",
  "message": "Version 2 is not the submitted, current version (submitted: 2, current: 3). Reload before deciding.",
  "path": "/api/invoices/41/approve", "fieldErrors": null }
StatusMeans hereUI reaction
400Invalid request / field validation (fieldErrors)Show each message next to its field; do not resend unchanged
401No, expired or invalid session — on the login form: wrong e-mail or passwordGo to login (keep the user's place); on the login form show the message
403Wrong role, or missing/invalid CSRF tokenRead message: CSRF → one GET /api/auth/me, then allow one retry; otherwise “not allowed”
404Not found or not yours (same answer on purpose)“Not found” — never hint that it exists
409State or version conflict, duplicate, closed batch, last admin, switched-off endpointReload the object, show the message; never auto-resend
415Wrong Content-TypeDeveloper error — fix the request
422Content rejected by a rule (upload code, submit check)Show code / message / fieldErrors
429Login locked for 15 minutesShow the message; do not retry automatically
500Unexpected server error (also a stored PDF failing its integrity check)“Something went wrong (reference errorId)” — never a stack trace

Not every route returns every status; the per-route lists are in REACT_BACKEND_HANDOFF.md. 502 exists only on the switched-off legacy extraction route.

States every screen needs

  • Loading: skeleton or spinner with an accessible label; up to a minute after idle (cold start) — say so.
  • Empty: an explanation and the next action (“No batches yet — create one”).
  • Error: the server message in a visible role="alert" region.
  • Retry: manual, only for network errors, 429 and 5xx.
  • Session expired: keep the place, show login, return after login.

  • Log out → 204; the next /api/auth/me → 401.

Reporting an API mismatch

Send the backend owner: the route and method, the request body (without any password), the HTTP status, the response body, the errorId if present, and what this guide or openapi.yaml says should happen. Never send cookies, tokens or passwords.

Hosting the React app later

The API is same-origin only: the browser must load React and call /api/** on the same scheme, host and port. Locally that is the Vite proxy.

  • A React site on frontend.onrender.com calling api.onrender.com directly does not work: two onrender.com hosts are different sites (Public Suffix List), the SameSite=Strict cookie is not sent, and the page cannot read XSRF-TOKEN.
  • Supported: one public hostname that serves the React build and forwards /api/* to the backend (reverse proxy / path-based routing). A Render Static Site rewrite to the API is a candidate, but forwarding of POST bodies and cookies has not been verified.
  • Never ask for Access-Control-Allow-Origin: *, SameSite=None or disabling CSRF. A separate API origin would be a deliberate, security-reviewed backend change.

Definition of done

  • All data comes from the documented routes through the one API client; no invented endpoints or fields.
  • Login, logout, session expiry and CSRF work in the browser through the proxy (shown live).
  • Navigation and screens per role; forbidden and not-found states handled.
  • Admin: users, categories, reviewer categories, intake/assignment, batches, queue status, dashboard.
  • Vendor: dashboard, batch create, one-by-one upload with per-file results, close, batch detail.
  • Reviewer: dashboard, assigned list, read-only invoice view with PDF.
  • Review/approval screens built from the contract and clearly labelled “not available in this demo”.
  • Loading, empty, error, retry and validation states everywhere; responsive to phone width; keyboard-only usable.
  • No secrets in code or VITE_*; no tokens in storage; no real data anywhere.
  • npm run lint, npm test and npm run build pass.

Glossary

API / endpoint / route
A URL plus an HTTP method that the backend answers, e.g. GET /api/admin/users.
Request / response
The message the browser sends (method, path, headers, optional body) and the backend's answer (status code, headers, body).
HTTP status
A number in the response: 2xx success, 4xx the request was not accepted, 5xx the server failed.
JSON / DTO
JSON is the text data format; a DTO (data transfer object) is the fixed shape of one JSON response or request, e.g. UserResponse.
Role
VENDOR, REVIEWER or ADMIN — decides which routes an account may call.
Cookie
A small value the browser stores per site and sends back automatically. HttpOnly cookies cannot be read by JavaScript.
CSRF
Cross-site request forgery: another website tricking your browser into sending a request. The X-XSRF-TOKEN header proves the request came from our own page.
Origin / same-origin
Scheme + host + port of a page. Same-origin means the page and the API share all three.
CORS
Browser rules for calls to another origin. This API grants none, on purpose.
Proxy
The Vite dev server forwarding /api/* to the real API, so the browser only ever talks to one origin.
Multipart / FormData
The request format for file uploads; the browser builds it from a FormData object.
Fixture
A prepared test file; here, the six synthetic PDFs the demo accepts.
